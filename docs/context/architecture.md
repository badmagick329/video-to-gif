# Architecture

How the app is put together, section by section. Only what is decided and built is here; each VTG Task adds the sections for what it builds. Terms are in [glossary.md](glossary.md).

## Shape

One repo, two halves, joined by Tauri 2 ([why](../decisions/2026-11-24-tauri-2.md)):

- **Frontend**, at the repo root: a pnpm package built by Vite ([package.json](../../package.json), [vite.config.ts](../../vite.config.ts), [tsconfig.json](../../tsconfig.json), Tailwind 3 through [tailwind.config.js](../../tailwind.config.js) and [postcss.config.js](../../postcss.config.js), [eslint.config.js](../../eslint.config.js), [index.html](../../index.html)). React 18 + TypeScript code is in `src/`. It runs in the system webview, WebView2 on Windows. Its layout is in *Frontend*.
- **Backend**, in `src-tauri/`: the standard Tauri 2 crate ([Cargo.toml](../../src-tauri/Cargo.toml), [tauri.conf.json](../../src-tauri/tauri.conf.json)). Identifier `ink.mgck.video-to-gif`, product name and window title `video-to-gif`.

`pnpm tauri dev` runs Vite's dev server and the Rust app together; the dev server only feeds the webview during development. The shipped app has no localhost server: the frontend reaches Rust only through IPC (*IPC boundary*).

## Frontend

The editor is the app's own desktop layout, drawn on the canvas board `Main.dc.html` ([why](../decisions/2026-11-24-editor-ui-from-canvas.md); VTG-9 says how to read the boards). Its settings were ported from mgck's advanced mode and keep that behaviour; mgck paths below are under `C:\code\python\web\mgck\frontend\src`.

- [main.tsx](../../src/main.tsx) imports the bundled fonts; [App.tsx](../../src/App.tsx) runs the startup check (*Finding ffmpeg*) and renders [SetupMessage.tsx](../../src/SetupMessage.tsx) or the editor, handing it the ffmpeg the check found for the status bar.
- `src/ipc/`: one module per Rust slice ([probe.ts](../../src/ipc/probe.ts), [preview.ts](../../src/ipc/preview.ts), [export.ts](../../src/ipc/export.ts)), mirroring that slice's IPC types and wrapping its commands. A new slice's commands get a module here.
- `src/editor/`: the editor. Components and hooks sit flat in the folder; `lib/` holds the logic without React; `__tests__/` holds the tests, with [tauri.ts](../../src/editor/__tests__/tauri.ts) standing in for the Tauri APIs and [harness.tsx](../../src/editor/__tests__/harness.tsx) rendering `SourceEditor` with a spy for Export. A later feature that is not part of the editor gets its own folder beside it.

**Window** ([Editor.tsx](../../src/editor/Editor.tsx)): a `100dvh` grid with `overflow: hidden`, so the page never scrolls. Rows: the 44 px toolbar ([Toolbar.tsx](../../src/editor/Toolbar.tsx): Open with Ctrl+O, the file name with its path as tooltip, the probe's chips from `sourceChips`, Close), the main area, and the 26 px status bar ([StatusBar.tsx](../../src/editor/StatusBar.tsx): the ffmpeg version, whether the player shows the source or a preview copy, the frame-memory figure, and the shortcuts button). The main area has two columns: the viewer over the 180 px timeline dock, and the 340 px inspector beside both. Only the inspector's tab body scrolls. [tauri.conf.json](../../src-tauri/tauri.conf.json) opens the window at 1280 × 800 with a 1100 × 700 minimum and keeps the native title bar. `Editor` holds the open source's trim, crop and settings, the export run and the session list (`useExport`), the destination (`useDestination`) and the frame-memory estimate (`useMemoryEstimate`), which the status bar and the export footer both show. With nothing open, the left column shows the drop prompt and *Open video…* (the start state is VTG-14's) and the Output tab a placeholder; the Exports tab works either way. [SourceEditor.tsx](../../src/editor/SourceEditor.tsx) is the main area with a source open.

**Viewer** ([VideoTrimmer.tsx](../../src/editor/VideoTrimmer.tsx), [Viewer.tsx](../../src/editor/Viewer.tsx)): `VideoTrimmer` owns the one `<video>` and lays out the left column. The viewer's header holds the mode switch and `CropControls` ([VideoCropper.tsx](../../src/editor/VideoCropper.tsx); the chosen ratio lives in `VideoTrimmer` because the box on the stage keeps to it). The mode is Source, Output or Side by side (the default), remembered in local storage under `video-to-gif.viewer-mode` (`useViewerMode`). The stage is measured (`useElementSize`) and each pane fits its picture's aspect into its half, or into the whole stage (`fitAspect`); jsdom has no ResizeObserver, so tests see a 960 × 540 stage. `SourceEditor` renders the output pane: `OutputPreview` under a label with the output size, frame rate and speed. In Output mode the source pane stays mounted, clipped to one pixel, because the output preview draws from the video's presented frames (`requestVideoFrameCallback`), which a video that is not rendered can stop presenting. While a proxy builds, its progress takes the stage (`PlaceholderColumn`). [ClipTransport.tsx](../../src/editor/ClipTransport.tsx) runs under the stage.

**Timeline dock** ([TimelineDock.tsx](../../src/editor/TimelineDock.tsx), [TimelineTrack.tsx](../../src/editor/TimelineTrack.tsx), [lib/timeline.ts](../../src/editor/lib/timeline.ts)): `VideoTrimmer` holds the selection and the playhead and renders the dock under the viewer. The header has In and Out fields (typed with `parseClipTime`), the length, Set in and Set out (the in or out point at the playhead, clamped by `setSelectionStart`/`End`), Whole video and the zoom slider. Under it, `TimelineTrack` draws the ruler, the track (thumbnails, the outside of the selection dimmed, the selection with its handles inside its edges) and the playhead across both; the handles and the playhead are sliders that step a frame per arrow. Pressing or dragging the ruler scrubs, pausing playback until release; on the track a press seeks, a handle drags its point, and the span moves the selection. Pointer edits land on frame boundaries (`snapToFrame`, `k / frameRate`), which is what lets the mouse set an exact frame.

The dock owns the view, `{ start, span }` in seconds: only that span is drawn, with positions as percentages of the track and anything outside clamped just past its clipped edges, so a 2-hour source at the deepest zoom never lays out a million-pixel element. The span runs from the whole source down to 48 frames (`deepestZoomFrames`), 15 px a frame at the window's minimum width. The slider is logarithmic, so each step zooms by the same factor on any length; it and Ctrl+wheel zoom keeping the playhead where it sits (centring it when out of view). The wheel and the scrollbar scroll a zoomed view; React's wheel listeners are passive, so the dock attaches its own to stop Ctrl+wheel zooming the page. When the playhead leaves the view, by playback or a jump, the view pages to it, except after the dock's own seeks: releasing the out handle returns the playhead to the in point without moving the view. `rulerTicks` labels the finest interval at least 72 px apart, whole frames below a second, and adds unlabelled ticks at the finest interval that divides it and stays 8 px apart: one frame at the deepest zoom. The header fits the 760 px left column at the 1100 px minimum window.

**Inspector** ([Inspector.tsx](../../src/editor/Inspector.tsx)): Output and Exports tabs. Both panels stay mounted and the inactive one is hidden, so the open sections and the footer's last notice survive a switch; tests switch tabs to reach what is on the other. The Output tab is [OutputSettingsForm.tsx](../../src/editor/OutputSettingsForm.tsx) in the board's sections: Format (a toggle per file type; the GIF encoder select, which holds only FFmpeg (palette) until VTG-15; WebP quality while WebP is on; Keep sound in MP4 while MP4 is on and the source has sound), Size, Timing, Transform, Captions, and a collapsed GIF quality & looping whose header summarises colours, dithering and plays. Under it, the pinned [ExportFooter.tsx](../../src/editor/ExportFooter.tsx) holds the estimate (frames and length, a row per ticked file type, *Estimating sizes*), the frame-memory warning, Save to (*Saving outputs*), and Export, labelled with the ticked file types and swapped for the run's progress and Cancel while it runs. The Exports tab (board `Exports.dc.html`) holds, while an export runs, [RunningCard.tsx](../../src/editor/RunningCard.tsx) and, under it, the session list [SessionResults.tsx](../../src/editor/SessionResults.tsx) (*Saving outputs*); during a run the same progress bar and Cancel (`RunProgress` in `ExportFooter.tsx`) are pinned under it too. Its badge, in the accent colour, counts the files made this session (failed file types left out) and is hidden at zero. Starting a run never switches tabs.

**Keyboard** ([lib/shortcuts.ts](../../src/editor/lib/shortcuts.ts), [useClipShortcuts.ts](../../src/editor/useClipShortcuts.ts)): Space, arrows, Shift+arrows, I and O, Home and End act on the player; Ctrl+Enter exports and Ctrl+O opens; `?` opens [ShortcutsOverlay.tsx](../../src/editor/ShortcutsOverlay.tsx), which Escape closes. The overlay lists every shortcut and the timeline's wheel gestures (Ctrl+wheel zooms, the wheel scrolls). A focused zoom slider keeps its arrows, Home and End.

Pixel figures always use the source's displayed size from the probe, never the player's: a proxy is smaller. Crops are stored as fractions of the frame (`ClipCrop`), so the box drawn over a proxy is the same box on the source; the crop readout, the full-frame check, width caps and output size multiply by the displayed size, which is what export crops. The output preview draws from whatever the player shows, using the same fractions.

mgck turns settings into ffmpeg arguments in `lib/discordgifs/single-pass-commands.ts` and `ffmpeg-commands.ts`, run by `ffmpeg-manager.ts`. None of these were copied: export builds arguments in Rust ([why](../decisions/2026-11-24-rust-owns-ffmpeg.md)), ported from them (*Exporting*). Captions are the exception that stays in the frontend: Export renders them to a PNG at the exact output size (`renderCaptionImage`), the same drawing the preview shows, for export to overlay.

## Slices

The Rust crate is vertical slices, one folder per feature under `src-tauri/src/`, each split into the layers it uses ([why, and when a layer is added](../decisions/2026-11-24-vertical-slices.md)):

| Slice | Layers | Owns |
| --- | --- | --- |
| [`probe`](../../src-tauri/src/probe/mod.rs) | domain, infrastructure, presentation | Finding `ffmpeg` and `ffprobe` (*Finding ffmpeg*), and reading a source's metadata with ffprobe (*Probing a source*). |
| [`preview`](../../src-tauri/src/preview/mod.rs) | domain, infrastructure, presentation | Opening a source for the player, deciding whether WebView2 plays it or a proxy, building proxies and timeline thumbnails, and the temp folder they live in (*Previewing a source*). |
| [`export`](../../src-tauri/src/export/mod.rs) | domain, application, infrastructure, presentation | Building ffmpeg arguments from the selection, crop and settings, running the jobs, streaming progress, cancelling, putting outputs in the destination folder, the frame-memory guard (*Exporting*), size estimates (*Estimating sizes*), the remembered destination, and opening or showing what a run made (*Saving outputs*). |

A layer appears with the first code that needs it: `domain` (types and rules, no I/O), `application` (use cases that coordinate infrastructure), `infrastructure` (processes, filesystem), `presentation` (the slice's `#[tauri::command]`s and the events it emits). Fill in a row's *Layers* when one appears.

- **Dependencies point inward.** [lib.rs](../../src-tauri/src/lib.rs) is the shell: it builds the Tauri app, is the only place that registers every slice's commands, and wires slices into app startup and exit. Within a slice, outer layers use inner ones. Across slices, only `domain` and the shared kernel are shared, and no slice imports the shell.
- **Shared kernel**: crate-level modules any slice's `infrastructure` may use. [process.rs](../../src-tauri/src/process.rs) and [search_path.rs](../../src-tauri/src/search_path.rs) find and start ffmpeg and ffprobe ([why](../decisions/2026-11-24-vertical-slices.md#amendment-2026-11-24-a-shared-kernel-for-spawning-ffmpeg)); [temp_folder.rs](../../src-tauri/src/temp_folder.rs) is the session temp folder ([why](../decisions/2026-11-24-vertical-slices.md#amendment-2026-11-24-the-temp-folder-joins-the-shared-kernel)). They import no slice.
- **Module paths name the layer** (`crate::probe::domain::…`), with no re-exports, so a wrong-way import shows in the `use` line.

## IPC boundary

Rust owns ffmpeg ([why](../decisions/2026-11-24-rust-owns-ffmpeg.md)). The frontend sends intent: the source path, the selection, the crop and the output settings, through `invoke` on a slice's command. Rust builds the ffmpeg and ffprobe arguments, runs the processes, and streams progress back as Tauri events. The frontend never builds a command line.

Everything crossing IPC from the frontend is a trust boundary: a slice's `presentation` validates it into `domain` types (paths exist, times and crop lie inside the source, settings are in range) before any process starts. ffprobe's output is another boundary, parsed and checked where it is read. Inside those boundaries, code trusts the domain types and fails fast.

Sources arrive as real filesystem paths, by native drag-drop or a file dialog, and are never copied ([why](../decisions/2026-11-24-real-paths.md)).

## Finding ffmpeg

v0 runs the user's own `ffmpeg` and `ffprobe`, found on PATH, and shows the setup message when either cannot run ([why](../decisions/2026-11-24-users-ffmpeg.md)).

- **Lookup** ([search_path.rs](../../src-tauri/src/search_path.rs)): PATH directories in order, and within each the PATHEXT extensions in order, matching regular files only, as `where.exe` does. `ffprobe` is looked for beside the resolved `ffmpeg` first, then on PATH, so both come from one build. The search reads the process's PATH on every call; nothing is cached, so a user who fixes PATH restarts the app.
- **Startup check** ([tools.rs](../../src-tauri/src/probe/infrastructure/tools.rs)): the `find_ffmpeg` command returns each tool as `found` (path and version from `-version`), `missing`, or `unusable` with a `reason`: a file that failed `-version`, or an ffmpeg older than 6.1, which lacks the `-stats_enc_pre` frame times export reads progress from (*Exporting*). Age is tested by capability, since nightlies report `N-<commit>` rather than a release: one 16×16 `nullsrc` frame through `-stats_enc_pre pipe:1`, about 40 ms, where `-h full` takes twice that and prints 1.3 MB. The setup message shows the reason (`ffmpeg 6.1 or newer is needed (this one is 6.0)`). [App.tsx](../../src/App.tsx) calls it on mount and renders [SetupMessage.tsx](../../src/SetupMessage.tsx) in place of the app unless both are `found`.
- **Spawning**: every ffmpeg and ffprobe process, in any slice, starts through [process.rs](../../src-tauri/src/process.rs), which sets `CREATE_NO_WINDOW` on Windows (a GUI app's console child would flash a window) and a null stdin. `command_at` with `Priority::Background` adds `BELOW_NORMAL_PRIORITY_CLASS` for work the user did not ask for (size estimates), so it runs on CPU time the player, an export and other programs leave over.

The owner's machine has two ffmpeg sets on PATH. Windows resolves `C:\scripts\` first (ffmpeg 9.0.1, gyan.dev full build), then the winget `yt-dlp.FFmpeg` nightly. `C:\scripts\` also holds a folder named `ffmpeg`, which is why Git Bash's `which ffmpeg` reports the winget copy; check with `where.exe ffmpeg`, which resolves as the app does. A test asserts the app's lookup matches `where.exe`'s first line.

To see the setup message, launch `src-tauri\target\debug\video-to-gif.exe` (from `pnpm tauri build --debug --no-bundle`) from a shell whose PATH drops every directory holding `ffmpeg.exe` or `ffprobe.exe`.

## Probing a source

The `probe_source` command takes an absolute path to an existing file and returns [source info](glossary.md), or a `ProbeError` tagged by `kind`: `ffprobeMissing`, `ffprobeFailed`, `notFound`, `unreadable` (ffprobe's last stderr line as `reason`), `noVideoStream`, `invalidOutput`. Types are in [domain.rs](../../src-tauri/src/probe/domain.rs), mirrored for TypeScript in [ipc/probe.ts](../../src/ipc/probe.ts); change both together.

[ffprobe/mod.rs](../../src-tauri/src/probe/infrastructure/ffprobe/mod.rs) runs `ffprobe -v error -hide_banner -show_format -show_streams -of json <path>` and validates the JSON:

- `-show_streams`/`-show_format` rather than `-show_entries`, because entry names such as `stream_side_data` differ between ffprobe versions and older ones reject them (gif-studio 1.1.1's fix).
- The video stream is the first one not flagged `attached_pic`, so cover art is skipped.
- Width and height are the displayed size: rotation comes from the display matrix in `side_data_list`, else the legacy `rotate` tag, and a quarter turn swaps the coded size. ffmpeg auto-rotates before filters, so crop rectangles use these pixels.
- Frame rate is `avg_frame_rate`, else `r_frame_rate`; values outside (0, 1000] count as absent. Duration is the format's, else the stream's; it must be positive.
- `container` is ffprobe's `format_name` as given, a comma-separated demuxer list (`mov,mp4,m4a,3gp,3g2,mj2`, `matroska,webm`).
- `audioCodec` is the first audio stream's `codec_name` (the stream the player and the proxy use), `"unknown"` when ffprobe names none, and `null` when there is no audio. It is the only field saying whether there is sound; TypeScript reads it through `hasAudio(info)`.

Tests run the real ffmpeg on PATH: they generate short `testsrc2` clips in temp dirs (H.264 MP4, AV1 MP4, HEVC MKV, VP9 WebM, no audio, 90° display rotation, audio only, a non-media file, and FLAC, Vorbis, MP3, Opus and AC-3 audio) and probe them, so `cargo test` needs ffmpeg with libx264, libsvtav1, libx265, libvpx-vp9, libopus, libvorbis and libmp3lame.

## Previewing a source

The user opens a source by dropping it anywhere on the window (Tauri's native drag-drop, `onDragDropEvent`; of several files the first opens), or by clicking Open in the toolbar (or *Open video…* in the empty viewer) or pressing Ctrl+O, which open `tauri-plugin-dialog`'s file dialog (permission `dialog:allow-open`). Either way the frontend gets a path and [useSource.ts](../../src/editor/useSource.ts) runs `probe_source`, then `open_source`, then plays the source or calls `make_proxy`. Results for an open that a newer one replaced are dropped. IPC types are in [preview/domain.rs](../../src-tauri/src/preview/domain.rs), mirrored in [ipc/preview.ts](../../src/ipc/preview.ts); change both together.

| IPC | Shape |
| --- | --- |
| `open_source(path, info)` command | `info` is the `SourceInfo` that `probe_source` returned, rechecked as untrusted. Returns `"source"` or `"proxy"`. Replacing the open source cancels its proxy build and deletes its proxy; reopening the same path keeps it. |
| `close_source(path)` command | Closes `path` if it is the open source: kills a running proxy build (waiting for ffmpeg to exit) and deletes its proxy and thumbnails. Any other path is ignored, so a close that raced a newer open cannot close it. Returns nothing. Close in the toolbar calls it. |
| `make_proxy(path)` command | Returns the proxy's path once built, or the existing one. `path` must be the open source. |
| `make_thumbnails(path, range?)` command | Returns the paths of 24 timeline thumbnails of the open source in time order, made from the proxy once it is built and from the source otherwise. Without `range`, or with one covering the whole source, the whole source's strip: made once, then returned as kept. With `range` (`{ start, end }` in seconds, end cut at the source's end) a new strip of that span; the session keeps the latest four range strips per source and deletes older folders. `path` must be the open source. |
| `proxy-progress` event | `{ source, progress }`, progress 0..1 from ffmpeg's `out_time_us` over the probed duration. |
| `PreviewError` | Tagged by `kind`: `notFound`, `invalidSourceInfo`, `notServable`, `notOpen`, `ffmpegMissing`, `proxyFailed` and `thumbnailsFailed` (ffmpeg's last stderr line as `reason`), `invalidRange` (a thumbnail range not finite, empty or outside the source), `cancelled` (the frontend ignores it). |

**Source or proxy** ([why](../decisions/2026-11-24-preview-source-or-proxy.md)): `choose_preview_source` plays the source when all three hold:

- the video codec is H.264, VP9 or AV1. HEVC always takes the proxy: WebView2 decodes it only with the HEVC Video Extensions and a capable GPU, so it played on the owner's machine but cannot be counted on elsewhere;
- the container is MP4 (`format_name` lists `mp4`, which also covers MOV) or Matroska named `.mkv` or `.webm`. ffprobe names MKV and WebM alike (`matroska,webm`) and Chromium reads both with one demuxer, so the extension only limits direct play to the names tested; `.mka` or a misnamed Matroska file takes the proxy;
- the audio is absent or one of the container's confirmed codecs, `MP4_AUDIO_CODECS` and `MATROSKA_AUDIO_CODECS`: AAC, MP3, Opus, Vorbis and FLAC in both.

Each video codec and container, and each audio codec in each container, was confirmed on generated clips (`testsrc2` plus a `sine` tone) in Chrome and in the app's WebView2: decoded frames counted, seeks landing, `webkitAudioDecodedByteCount` growing, and the tone reaching Web Audio as non-silent samples before and after a seek. Everything else takes the proxy: DTS decoded in neither browser; AC-3 and E-AC-3 decoded in WebView2 on the owner's machine but not in Chrome (Edge uses the Windows Dolby decoder, which not every install has, so like HEVC they depend on the PC); PCM decoded in both but is outside the set the owner admitted. The audio check matters because undecodable audio raises no `error`: the video plays silently. The owner's 2.4 GB 4K H.264/FLAC MKV now opens in under half a second instead of a one-minute proxy, with sound, and seeks across it land in 0.3 to 0.8 s. When the player raises `error` on the source, or shows no picture (`videoWidth` 0), the frontend switches to a proxy.

**Proxy** (`proxy_args` in [preview/domain.rs](../../src-tauri/src/preview/domain.rs)): `-map 0:V:0` (skips cover art) plus `-map 0:a:0` when the source has audio; `scale` to at most 720 high from the displayed size, never upscaled, both sides even; `-fps_mode passthrough`; `libx264 -preset ultrafast -crf 23`; `-force_key_frames expr:gte(t,n_forced)` (a keyframe a second, for scrubbing); stereo AAC 128k; `-movflags +faststart`; `-progress pipe:1`. There is no `-ss`, `-copyts` or `-r`, so the proxy starts at 0 at the source's first timestamp and time t in the player is t after the source's start, the offset export's input `-ss` measures (a test checks this on a source starting at 2.5 s). The player at t shows the frame whose span holds t, while input `-ss t` starts at the first frame at or after t, up to one frame later; export seeks a frame early to match (*Exporting*). A 2.4 GB 4K H.264/FLAC MKV of 187 s took about a minute to proxy on the owner's machine, before MKV played directly.

**Thumbnails** (`thumbnail_args` in [preview/domain.rs](../../src-tauri/src/preview/domain.rs)): ffmpeg writes `thumb-01.jpg` to `thumb-24.jpg`, 72 high, one per equal slice of the strip's span, sampled at the slice's middle. A span up to 90 s is one decoding pass: input `-ss` to the first slice's middle, then `fps=1/slice` (`tpad` repeats the last frame first, or `fps` stops short at the last decoded frame), so each thumbnail is the first frame at or after its slice's middle. A longer span seeks instead: one input per slice with `-skip_frame nokey -noaccurate_seek -threads 1 -ss <middle>`, one frame out of each, so each thumbnail is the last keyframe before its time and ffmpeg reads 24 keyframes, not the file. On the owner's 2-hour 1080p H.264 recording (a keyframe every 3 s, played directly) that takes 2.5 s for the whole strip or any long range, where gif-studio's single keyframes-only pass (`makeStrip`, v0's method) took 44 s because it still demuxes every packet; a 60 s range takes 2.3 s and a 4 s range 0.5 s (`range_strips_on_a_long_recording`, an ignored test run by hand with `VTG_LONG_CLIP`). mgck seeks a hidden `<video>` 24 times instead; measured in Chrome, that took 2.8 s on the 4K MKV's 720p proxy but 20 s on a 120 s 4K H.264 MP4 with a keyframe every 10 s, where the ffmpeg pass takes 0.7 s. A source played directly is its own thumbnail input, so a built proxy is preferred. The dock shows a plain bar until the whole strip arrives, and when the command fails. Zoomed past 1.5×, once the view has been still for 300 ms, `useRangeThumbnails` asks for a strip of the view plus half a view either side; each thumbnail is drawn at its own time over the whole strip, tiled at its own aspect, and the last range strip stays up until a later one arrives.

**Asset protocol**: the webview loads sources, proxies and thumbnails from `http://asset.localhost/<path>` (`convertFileSrc`). [tauri.conf.json](../../src-tauri/tauri.conf.json) enables the protocol (Cargo feature `protocol-asset`) with an empty scope; [preview/presentation.rs](../../src-tauri/src/preview/presentation.rs) allows this session's temp folder and its subfolders at startup and each source file as it opens, export allows each output as it is made (*Saving outputs*), and any other path gets 403. Responses carry `Access-Control-Allow-Origin` for the app's origin, so the editor's `<video>` elements set `crossOrigin='anonymous'`: without it their frames taint the output preview's canvas and it draws nothing. Tauri's scope cannot shrink, so a session's earlier sources stay readable until exit. Range requests get 206 with at most 1000 KB per response, and the `<video>` element always sends `Range`: a 2.75 GB file opened and seeked with the app's memory under 50 MB. A request without `Range` reads the whole file into memory, so anything else fetching a source sends one.

**Temp folder** ([temp_folder.rs](../../src-tauri/src/temp_folder.rs), in the shared kernel; the preview slice creates and deletes it): `%TEMP%\video-to-gif\session-<pid>\` holds `proxy-<n>.mp4` files, `thumbs-<n>` folders, export's `captions-<n>.png` while an export or size estimate runs, a size estimate's `estimate-<n>.<ext>` samples until each is measured, and a `lock` file the running app keeps locked. At startup the app deletes every entry in `%TEMP%\video-to-gif` except session folders whose lock another running copy holds, so a crashed session's proxies go and a second running app's stay. A proxy and its source's thumbnails live while the source stays open; [session.rs](../../src-tauri/src/preview/infrastructure/session.rs) deletes them when another source replaces it or the user closes it (`close_source`). On `RunEvent::Exit` (after the last window closes) the app stops a running size estimate and cancels a running export (*Exporting*), kills a running proxy encode, waits for ffmpeg to exit so no file stays locked, then deletes its session folder and, when nothing else is in it, `%TEMP%\video-to-gif`.

To drive the preview in the real app, launch the debug build with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` and evaluate JS over CDP (`http://127.0.0.1:9222/json`); `window.__TAURI_INTERNALS__.invoke` reaches the commands. The debug build opens a console window beside the app; the release build does not.

## Exporting

The `export` slice turns an export request into outputs. IPC types are in [export/domain/](../../src-tauri/src/export/domain/) (`plan.rs` for the request, `outcome.rs` for results, `memory.rs` for the estimate), mirrored in [ipc/export.ts](../../src/ipc/export.ts) and, for the request itself, `ExportRequest` in [editor/lib/types.ts](../../src/editor/lib/types.ts); change both sides together.

| IPC | Shape |
| --- | --- |
| `run_export(request, destination)` command | `request` is `{ path, info, trim?, crop?, settings, keepSound, captions?, acceptPaging? }`: the source path, the `SourceInfo` `probe_source` returned (rechecked), the selection, the crop as fractions, the `OutputSettings` (mgck's `AdvancedSettings`), the caption PNG as bytes, and whether the user chose Export anyway (*Frame-memory guard*). `destination` is an existing folder (*Saving outputs*). Cancels a running size estimate. Resolves, once every ticked file type has settled, with `ExportOutput[]` in run order. |
| `cancel_export()` command | Kills the running export's ffmpeg; that output and those not yet started settle as `cancelled`. Returns at once. |
| `estimate_export_memory(request)` command | `request` is `{ info, trim?, crop?, settings }`. Returns `{ heldBytes, availableBytes, limitSeconds, fits }` (*Frame-memory guard*). |
| `export-progress` event | `{ fileType, progress }`, progress 0..1 per file type, from the frame times ffmpeg writes (*Progress*): 0 at its start, rising in steps of at least 0.5%, never backward, and 1 when it is saved. |
| `export-output` event | One `ExportOutput` as it settles: `{ status: 'done', fileType, path, size, width, height }` (bytes, encoded pixels), `{ status: 'failed', fileType, reason }` (the last lines of ffmpeg's stderr, or the filesystem's error) or `{ status: 'cancelled', fileType }`. |
| `ExportError` | Rejects `run_export` (or an estimate) before anything runs. Tagged by `kind`: `notFound`, `destinationNotFound`, `invalidRequest` (`reason`), `ffmpegMissing`, `notEnoughMemory` (`heldBytes`, `availableBytes`), `busy` (one export at a time; a size estimate during an export), `captionsFailed`. |

**Validation** (`ExportRequest::validate` in [plan.rs](../../src-tauri/src/export/domain/plan.rs)): settings are clamped to mgck's `settingLimits` (width 16 to 4096, fps 1 to 60, GIF colours 2 to 256, WebP quality 1 to 100), speed to 0.25 to 3, plays to 0 to 65535; file types are sorted into GIF, WebP, MP4 and de-duplicated, and at least one is required. The selection must lie in the source and the crop in the frame. Rust works out the output size (`output_size`, mgck's `outputSize`) from `info`'s displayed size, the crop and the rotation, and the output length (`output_seconds`) from the selection, speed and direction; the frontend's own figures for these are not sent. A caption PNG must be exactly that size. Sound stays only when asked, the source has sound, and `sound_drop_reason` allows it (forward, 0.5× to 2×). Caption text and size are not read: the PNG carries them.

**Arguments** (`single_pass_args` in [args.rs](../../src-tauri/src/export/domain/args.rs)): mgck's `buildSinglePassCommand`, `cropFilter` and `trimInput`, with mgck's test cases as unit tests. One ffmpeg run per file type, filters in Gif Studio's order: crop (fractions of `iw`/`ih`, which ffmpeg evaluates on the auto-rotated frame), rotate, flips, `setpts` speed, `fps`, lanczos `scale`, caption overlay, then direction. GIF: `palettegen stats_mode=diff` and `paletteuse diff_mode=rectangle`, `-loop` as repeats. WebP: `libwebp_anim` ([why](../decisions/2026-11-24-webp-anim-encoder.md)), `-loop` as plays. MP4: libx264 CRF 20 `medium`, `yuv420p`, `+faststart`, and with sound `-map 0:a:0? -c:a aac -b:a 160k`, `atempo` at other speeds, `-shortest`. The builder is split so size estimates reuse it: `video_chain` (crop through scale) and `encoder` (direction, encoder graph and options per file type) are shared by the export's `pass_args` and the estimate's sample builders (*Estimating sizes*). `single_pass_args` is mgck's command exactly; the app runs `job_args`, which prefixes `-hide_banner -loglevel error -nostats -n -nostdin` (stderr holds only errors, nothing is ever overwritten) and adds progress reporting (*Progress*) without changing a byte of the output.

**Progress** ([progress.rs](../../src-tauri/src/export/domain/progress.rs), read by [job.rs](../../src-tauri/src/export/infrastructure/job.rs)): ffmpeg's `-progress` report follows the muxed file and stays silent until every output has started, so a GIF sat at 0 through `palettegen` (which reads the whole input before the first frame is dithered), `reverse` held everything until the input ended, and libwebp_anim writes its one packet at the end. Instead:

- Every run writes `encoded=<seconds>` to stdout as each video frame enters the encoder (`-stats_enc_pre:v:0 pipe:1` with `-stats_enc_pre_fmt`), one flushed line a frame.
- A GIF (any direction) and any Reverse also split the selection, just before the direction filter, into a second output: the tap, `-map [tap] … -f null -`, writing `tapped=<seconds>`. It moves while the input is read. A null output only takes references to frames the graph makes anyway: outputs are byte-identical to `single_pass_args`'s (a test compares them), and wall time on a 20 s 1080p clip stayed within run-to-run noise.
- Progress is the encoded fraction of the output's seconds; with a tap it is `share × tapped + (1 − share) × encoded`, the tap's fraction measured against the selection played once. `tap_share` is 0.4 for GIF and 0.2 for a reversed WebP or MP4, from timing where each spends its run. Boomerang WebP and MP4 encode the forward half as it is read, so they need no tap.

**Trim**: input `-ss` and `-t` before `-i`, so only the selection is decoded and encoded. `-ss` is `seek_start(start)`: the trim start minus one source frame (`1 / info.frameRate`) plus 1 ms, which keeps exactly the frame the player showed at the trim start (*Previewing a source*); plain `-ss start` started up to a frame late. A test exports from a clip whose frames carry their own number in their brightness and checks the first output frame. A variable-frame-rate source can still start a frame off where frames bunch up, since the step is the probe's average.

**Running** ([application.rs](../../src-tauri/src/export/application.rs)): `run` takes progress and output callbacks, which `run_export` turns into events, so the whole run is tested without a Tauri app. It refuses a run that does not fit in free memory unless the request accepts paging, writes the caption PNG as `captions-<n>.png` in this session's temp folder ([temp_folder.rs](../../src-tauri/src/temp_folder.rs) `session_dir`), then runs the ticked file types one at a time in the order GIF, WebP, MP4, each through [process.rs](../../src-tauri/src/process.rs). A file type that fails is reported and the rest still run, as in mgck. The caption file is deleted when the run ends, however it ends. `Exports` (Tauri state) allows one export at a time; on app exit it cancels the running one and waits up to 5 s for it to clean up, before preview deletes the temp folder.

**Output files** ([outputs.rs](../../src-tauri/src/export/infrastructure/outputs.rs)): ffmpeg writes each output to `<stem>.part-<pid>-<n>.<ext>` in the destination folder (the extension stays last because ffmpeg picks the muxer from it). Only when ffmpeg exits with success is the file moved to its name, mgck's `singlePassDownloadName` (`dance.mov` becomes `dance.gif`); a taken name becomes `dance (1).gif`, `dance (2).gif` and so on. The move is `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`, which claims a name and fails if it exists in one step, so two runs finishing together never share a name and nothing is overwritten (`std::fs::rename` would replace). On a non-zero exit or a cancel, the `.part` file is deleted once ffmpeg has exited, so the folder only ever gains finished outputs (gif-studio's OSS-4 item 1). Only a crash or power cut can leave a `.part` file.

**Frame-memory guard** ([memory.rs](../../src-tauri/src/export/domain/memory.rs), gif-studio's OSS-4 item 3): mgck's `heldCopies` and `frameMemoryLimitSeconds`. A GIF queues every frame for its palette (one copy), `reverse` holds the whole selection (one more), and Boomerang adds its forward half to the GIF queue, at 4 bytes a pixel; forward WebP and MP4 stream and hold nothing. The budget is free physical memory, `GlobalMemoryStatusEx`'s `ullAvailPhys` ([infrastructure/memory.rs](../../src-tauri/src/export/infrastructure/memory.rs)), read when the estimate or the run asks; off Windows it is unknown and nothing is refused. The guard warns and never blocks (VTG-9): `estimate_export_memory` gives the UI the figures to warn with, and the user may export anyway, which sends `acceptPaging: true`. `run_export` refuses with `notEnoughMemory` only when the held bytes exceed free memory and the request lacks that flag, so no caller pages the machine by accident.

Integration tests in [application/tests.rs](../../src-tauri/src/export/application/tests.rs) run the real ffmpeg on clips generated at test time (`testsrc2`, `sine`, a frame-counting `geq` clip, a marked frame, a 90° `-display_rotation` copy) and check every file type with ffprobe and decoded frames: size, duration, loop count (the GIF's NETSCAPE extension, the WebP's ANIM chunk), sound, orientation, caption pixels, a cancelled and a failed run leaving nothing, a numbered name, and GIF and WebP progress rising through the run (forward and reverse) with output identical to mgck's command. `cargo test` therefore also needs ffmpeg with libwebp_anim and libx264.

## Estimating sizes

Before Export, the export footer shows each ticked file type's expected size as "≈ size". The app reports the figure and never judges it (VTG-9). Rust estimates it from sample encodes of the export request, in the background. Types are in [estimate.rs](../../src-tauri/src/export/domain/estimate.rs), mirrored in [ipc/export.ts](../../src/ipc/export.ts).

| IPC | Shape |
| --- | --- |
| `estimate_output_size(request, onEstimate)` command | `request` is `run_export`'s. `onEstimate` is a Tauri `Channel` that receives each file type's `SizeEstimate` as it settles: `{ status: 'done', fileType, bytes }`, `{ status: 'failed', fileType, reason }` (a sample failed, or a whole encode would not fit in free memory) or `{ status: 'cancelled', fileType }`. Resolves with all of them in run order. Starting one cancels the running one; during an export it rejects `busy`. |
| `cancel_size_estimate()` command | Kills the running estimate's ffmpeg. Returns at once. |

**Methods** ([domain/estimate.rs](../../src-tauri/src/export/domain/estimate.rs)), measured against full exports on four clips (VTG-10 holds the table):

- **GIF**: three 1 s windows (output seconds, so at 2× each reads 2 s of source), joined before `palettegen` so they share one palette, scaled by output frames over sampled frames. A palette per window overestimated busy footage by 15 to 23%.
- **WebP**: six 0.5 s windows read through the first-frame model, `overhead + first frame + (N − 1) × mean later frame`, each part the median over the windows. Sizes come from the `ANMF` chunks; frame slots are counted from `-stats_enc_pre` lines, since libwebp_anim merges repeated frames.
- **MP4**: the whole export, exact. Sampling static footage was off by up to 275%.
- Window *i* of *k* is centred at `start + (i + 0.5) × length / k`. A selection no longer than a file type's windows together is encoded whole. A whole encode whose held frames would not fit in free memory is not run: a background estimate never pages the machine.

**Running** ([application/estimate.rs](../../src-tauri/src/export/application/estimate.rs)): samples are the export's own arguments (`video_chain` and `encoder` in [args.rs](../../src-tauri/src/export/domain/args.rs)), so crop, speed, direction and captions reach them, started through `Job::start_in_background` (below-normal priority, *Finding ffmpeg*). They write `estimate-<n>.<ext>` into the session temp folder and each file is deleted once measured. For a selection up to 20 s, GIF and WebP are sampled by one ffmpeg (`shared_sample_args`) that decodes the selection once, as the export does, and feeds every output through its own `-filter_complex`, which ffmpeg runs on its own thread; windows are `trim` spans inside it. Decoding is most of a 1080p sample's cost, and separate runs decode each window from its keyframe. A longer selection gives GIF and WebP their own runs (GIF's windows as input-seeked inputs of one run, `windowed_sample_args`; a run per WebP window). MP4 always runs on its own, at the same time: in one process with a GIF, which holds every frame until its palette is made, x264's streaming output deadlocked ffmpeg's scheduler (ffmpeg 9.0.1, a whole GIF plus MP4 of a 20 s 1080p H.264 talk; the process sat idle). GIF with WebP, and the export's GIF with its tap, do not. Each estimate ffmpeg logs `[<unix ms>] estimate: started ffmpeg for …` to stderr, visible in the debug build's console.

**Speed and accuracy**: GIF sets the pace. Its `palettegen` and `paletteuse` (sierra dithering) run on one thread after every sampled frame has arrived, about 1.4 s for 45 frames at 480 × 270 and 4 s for 72 at 640 × 360 on the owner's 12-thread PC, so 640 px/24 fps on a busy 1080p clip takes 5 s or more however the samples are scheduled. Estimates run below normal priority, so a game or export running at the same time slows them in turn. Errors on the busy 1080p clip: GIF within 2.6%, WebP within 7.6%, MP4 exact, Reverse and Boomerang within 7%. `estimate_accuracy` ([estimate_accuracy.rs](../../src-tauri/src/estimate_accuracy.rs), an ignored test in the shell because it needs the `probe` and `export` slices) reruns this on any clips: set `VTG_ESTIMATE_CLIPS` to paths separated by `|`, then `cargo test --release --lib estimate_accuracy -- --ignored --nocapture`; `VTG_ESTIMATE_TYPES=gif,mp4` narrows the file types and `VTG_ESTIMATE_NO_EXPORT=1` times estimates without exporting.

**Scheduling** ([useSizeEstimate.ts](../../src/editor/useSizeEstimate.ts)): an estimate starts 1.5 s after the last change to the selection, crop or settings; any change kills the running one at once (`cancel_size_estimate`). It waits while the video plays (`usePlaying`) or an export runs. Each file type's figure is keyed on what its size depends on (`estimateKeys`): GIF colours and dithering affect only GIF, WebP quality only WebP, keep sound only MP4, anything else all. A run asks only for the ticked file types whose figure is missing or out of date, so unticking and ticking a file type again asks for nothing. Each file type's row in the export footer shows a placeholder while no figure exists, the figure when it matches the settings, and the old figure greyed while a newer one runs; a note under the rows says which ([ExportFooter.tsx](../../src/editor/ExportFooter.tsx), states from the canvas board `Estimate.dc.html`). [estimate.test.tsx](../../src/editor/__tests__/estimate.test.tsx) drives this under fake timers, counting `estimate_output_size` calls while the width slider is dragged.

## Saving outputs

Export hands the export request, the active destination and each file type's ready size estimate to `run_export` through [useExport.ts](../../src/editor/useExport.ts), which lives in [Editor.tsx](../../src/editor/Editor.tsx) so a run and the session list outlast the clip. It listens to `export-progress` and `export-output` for the page's lifetime (a per-run `listen` could register after a fast run's first events) and keeps the run as an `ExportJob` ([lib/export-run.ts](../../src/editor/lib/export-run.ts)): the file type being made, its progress and start time, each settled file type's output, and the estimates. A settled file type moves the job to the next one at once, before its first progress event.

- **Running card** ([RunningCard.tsx](../../src/editor/RunningCard.tsx)), in the Exports tab while a run lasts, like a render queue: a row per ticked file type in run order. A finished one shows ✓ and its actual size; failed and cancelled ones say so; the one being made shows its percent, the time left (`secondsLeft`: its pace so far, shown once it is 2% done and a second in), `est` and its size estimate, and a bar; the rest show Queued. The header says how long ago the run started; a one-second clock keeps both moving between events.
- **Footer** (`RunProgress` in [ExportFooter.tsx](../../src/editor/ExportFooter.tsx)): the overall bar, finished file types counted in full, labelled `Making WebP (2 of 3) · 42%` with the current file type's percent (`Making GIF (1 of 3), analysing colours…` before a GIF's first frame), and Cancel, in Export's place in the footer and pinned under the Exports tab.
- **Session list** ([SessionResults.tsx](../../src/editor/SessionResults.tsx)), headed *This session* with the newest output's folder: each output as its event arrives, newest first, with a 56 × 62 thumbnail (`<img>` for GIF and WebP, the first frame of a muted `<video>` for MP4), the file name, then format · W × H · size, and Open, Show in folder and Copy. The outputs `run_export` resolves with fill in any event that never came, each file type listed once. A cancelled file type is not listed; a failed one shows its reason in a folded `<details>`. The list lives in `Editor`, so opening another video keeps it.

When the run ends, a line under Export says what was saved where, what failed, or that it was cancelled; an `ExportError` gets a short sentence, with Rust's `reason` in a folded `<details>`.

| IPC | Shape |
| --- | --- |
| `saved_destination()` command | The folder picked with Save to on this or an earlier launch, or `null` when none was picked or it fails the load check below. |
| `remember_destination(folder)` command | Remembers `folder` (an absolute path to an existing folder, else `DestinationError` `notFound`), or forgets the choice with `null`. A write failure is `notSaved` (`reason`). |
| `open_output(path)` command | Opens an output in its default app. |
| `show_output_in_folder(path)` command | Opens Explorer on the output's folder with the file selected. |
| `copy_output(path)` command | Puts the output on the clipboard as a file (*Copy* below). |
| `OutputError` | Rejects the three above. Tagged by `kind`: `notAnOutput` (not made this session), `missing` (moved or deleted since), `shellFailed` (`reason`), `clipboardFailed` (`reason`, usually another program holding the clipboard). |

**Destination** ([useDestination.ts](../../src/editor/useDestination.ts)): the remembered folder when Rust offers one, else the source's folder (`sourceFolder`, which keeps the backslash of a drive root: `C:` alone means the drive's current directory). The Save to row above Export shows the active folder (its tooltip marks the default as the video's folder), opens with Change… `tauri-plugin-dialog`'s folder picker (`directory: true`, under the existing `dialog:allow-open`) and offers *Use the video's folder* once one is picked. Rust keeps the choice as `destination.json` (`{ "folder": … }`) in the app config dir, `%APPDATA%\ink.mgck.video-to-gif` ([destination.rs](../../src-tauri/src/export/infrastructure/destination.rs)). The file is read as untrusted: it counts only when it parses and names an absolute path to an existing folder. A folder that has gone is not offered but stays in the file, so a drive plugged back in brings it back on the next launch. A folder deleted mid-session makes `run_export` refuse with `destinationNotFound`.

**Open, Show in folder and Copy** ([presentation.rs](../../src-tauri/src/export/presentation.rs)): as `run_export` reports each finished output, before its event is emitted, Rust records the path in `SessionOutputs` ([session_outputs.rs](../../src-tauri/src/export/application/session_outputs.rs)) and adds that one file to the asset protocol's scope, so the list can draw its thumbnail and nothing else in the destination becomes readable. All three commands accept a path only when it equals, byte for byte, one recorded this session and the file still exists; the webview is a trust boundary, and without the check any script in it could have the shell open, or the clipboard hand out, any file. Open and Show in folder then call `tauri-plugin-opener`'s `open_path` and `reveal_item_in_dir` (`SHOpenFolderAndSelectItems`) from Rust on a blocking thread. The plugin is a Rust dependency only, never registered, so the webview gets none of its commands and the capability file is unchanged.

**Copy** ([clipboard.rs](../../src-tauri/src/export/infrastructure/clipboard.rs)): puts the output on the Windows clipboard as `CF_HDROP`, the format Explorer's own Ctrl+C on a file uses, so it pastes into an Explorer folder as a copy and into chat apps as an attachment. `drop_files` builds the payload as a pure function: a 20-byte `DROPFILES` header (`pFiles` 20, `pt` 0,0, `fNC` 0, `fWide` 1), then each path in UTF-16LE with its NUL, then a final NUL; its tests check those bytes, so no test touches the real clipboard. `copy_files` is the thin call: `clipboard-win` (a Windows-only dependency) opens the clipboard with up to 10 retries 5 ms apart, sets the payload (emptying the clipboard first), and adds `Preferred DropEffect` = `DROPEFFECT_COPY`, so a paste copies rather than moves. The button reads *Copied* for 1.5 s. Elsewhere than Windows the command fails with `clipboardFailed`.

**Frame-memory warning** ([useMemoryEstimate.ts](../../src/editor/useMemoryEstimate.ts)): `estimate_export_memory` runs 150 ms after the selection, crop or settings last changed. When `fits` is false, an alert names what holds the frames (Reverse, Boomerang or the GIF's palette pass), the bytes held and free, says Windows will page to disk and the PC may crawl, and offers `limitSeconds` as the longest selection that stays in memory; Export becomes **Export anyway** and sends `acceptPaging: true`. When the frames fit but take more than half the free memory, a softer note says so. Frames that stream (`heldBytes` 0) show nothing.
